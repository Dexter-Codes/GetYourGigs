# Get Your Gigs

A working marketplace with **one account that can hire or work**, an ASP.NET Core monolith, a React web app, and native .NET MAUI apps. The supplied HTML MVP defines the workflows; the supplied mobile reference informs the ivory, coral, serif typography, colorful categories, compact cards, and five-tab navigation.

## Run locally

Requirements: .NET SDK 10.0.400 or a newer 10.0 feature band, Node 20.19+ (Node 22 recommended), Python 3, and PostgreSQL command-line tools. This machine already has these installed.

```sh
./scripts/dev.sh
```

Open **http://localhost:5080**. The script starts an isolated, loopback-only PostgreSQL cluster in `.local/postgres` on port **55432**, creates an ignored development signing key, builds React, applies EF migrations, and starts the monolith. Uploads live in `src/GetYourGigs.Api/.data/uploads`.

In Development without SMTP, the email form **explicitly displays a test verification code**. No email is sent. Codes expire after 10 minutes, allow five failed attempts, and can be used once. Production never returns the development code.

Optional demonstration data is created by `--seed` **only if the database has no accounts**. Every seeded listing is labeled as a sample. There are **no seeded ratings or fabricated reviews**. Local test accounts:

- `hirer@example.test` — posted gigs, Hiring context.
- `jahan@example.test` — talent profile, Working context.

Use the email-code form to enter either local account. These are not externally deliverable email addresses. A QA posting and talent profile created during browser verification remain in the local development database and are explicitly labeled as samples. They are not part of the seed source.

For live React development, run the API, then:

```sh
npm run dev --prefix src/GetYourGigs.Web
```

Vite serves **http://localhost:5173** and proxies API/media requests to port 5080. The production React build is served directly by the monolith, so a separate frontend server is unnecessary.

## Projects

| Project | Responsibility |
|---|---|
| `src/GetYourGigs.Api` | One ASP.NET Core process: authentication, endpoints, services, EF Core/PostgreSQL, uploads, React hosting |
| `src/GetYourGigs.Contracts` | Immutable request/response records and shared lifecycle enums |
| `src/GetYourGigs.Client` | Reusable, source-generated JSON HTTP client and token-store contract; no business policy |
| `src/GetYourGigs.Web` | React + TypeScript + Vite UI and reusable components/forms |
| `src/GetYourGigs.Mobile` | Native MAUI XAML/MVVM for Android, iOS, and Mac Catalyst; secure device token storage |
| `tests/GetYourGigs.Tests` | Integration tests exercising actual ASP.NET endpoints and PostgreSQL transactions |

The API uses feature services and minimal endpoint groups. It does not introduce microservices, MediatR, generic repositories, or another role-specific account system. Detailed decisions and business rules are in [architecture.md](docs/architecture.md).

## Included workflows

- Anonymous Hiring/Working preview, capped to three returned listings on the server; the React UI blurs placeholder cards rather than downloading hidden profiles.
- Verified email-code login and Google token validation. The same verified email resolves to the same account across providers.
- Server-persisted Hiring/Working preference; context-specific Discover, Gigs, and Saved.
- Five-question talent onboarding, immediate publishing, editing, availability, rate units, skills, and up to five photos.
- Three-step create/edit gig form with calendar dates, optional date/budget, photos, ownership checks, and closing.
- Application notes, optional quotes, a transactional three-per-IST-day cap, and withdrawals that do not refund the cap.
- Shortlisting, booking, declining, automatic sibling waitlisting, cancellation of conflicting same-date applications, and cross-hirer double-booking protection.
- Explicit completion, completed-only reviews, a unique review per completed application, and ratings derived from real reviews.
- Participant-only inboxes, persistent messages, unread counts, and asynchronous replies. Open conversations refresh every 10 seconds.
- Bookmarks and activity events generated by actual applications, messages, booking cascades, completion, and reviews.
- Native device image selection/upload and server-side signature/size checks for JPEG, PNG, and WebP.

## Mobile

Install the MAUI workload if it is missing:

```sh
dotnet workload install maui
```

On a Mac with Xcode and the iOS simulator runtime:

```sh
dotnet build src/GetYourGigs.Mobile -f net10.0-ios \
  -p:MobileTargetFramework=net10.0-ios -r iossimulator-arm64
```

Android:

```sh
dotnet build src/GetYourGigs.Mobile -f net10.0-android \
  -p:MobileTargetFramework=net10.0-android
```

Supply `-p:AndroidSdkDirectory=/your/android/sdk` when it is outside the standard location. Open the solution in VS Code with the MAUI tooling or your preferred MAUI IDE to choose an emulator/device and debug.

Debug defaults: **iOS simulator → localhost:5080**, **Android emulator → 10.0.2.2:5080**. You can change the API URL on the sign-in screen, even before an account exists, or in Profile. Changing servers signs out the device. A physical device needs a reachable server address; release URL configuration requires HTTPS. Debug Android permits local HTTP; release Android does not. Native Google sign-in uses the hosted React sign-in in the system browser and a one-minute, single-use code bound to a SHA-256 proof key; bearer tokens are never put in callback URLs.

The mobile root tabs are Home, Gigs, Post, Messages, and Profile; Saved and Updates are accessible in the header. Native and web share the API and C# contracts, while each has UI suited to its platform.

## Configure real sign-in and hosting

Use environment variables, .NET user-secrets, or the ignored local configuration file. **Do not put secrets in React, MAUI source, or tracked appsettings files.** See [.env.example](.env.example) for names.

- `ConnectionStrings__Database`: PostgreSQL connection string. Use certificate-validated TLS with a hosted database.
- `Jwt__Key`: a stable random secret of at least 32 characters. Development creates an ignored local key; production requires an explicit key. Tokens expire after 12 hours; sign-out clears the device token. Server-side token revocation/refresh sessions are not implemented.
- `Google__ClientId`: your Google web OAuth client ID. Add the exact hosted web origin to Google's allowed JavaScript origins. Google buttons remain hidden until configured. Both web and native browser sign-in use server validation of the issuer/audience and verified email.
- `Smtp__Host`, `Smtp__Port`, `Smtp__User`, `Smtp__Password`, `Smtp__From`: a real transactional email service with STARTTLS.

PostgreSQL itself is free to run locally. For managed hosting, [Neon's free plan](https://neon.com/pricing) and [Supabase's free plan](https://supabase.com/pricing) are compatible options, subject to their current storage/compute/inactivity limits. No hosted database account was provisioned and the prototype's live Supabase data was not changed or imported. The backend can use a standard PostgreSQL connection from either provider through Npgsql; it does not depend on PostgREST or permissive browser-side RLS policies.

Apply migrations as a release step, then start the service normally:

```sh
dotnet run --project src/GetYourGigs.Api --no-launch-profile -- --migrate --migrate-only
```

Set `ASPNETCORE_ENVIRONMENT=Production` and the real connection string/signing key for deployment. Only Development auto-migrates on normal startup. Host the monolith behind HTTPS; configure trusted proxy/forwarded headers according to your hosting environment. Persist and back up PostgreSQL and media. Local development stores photos in `.data/uploads`; hosted Render testing uses the Supabase Storage adapter with stable `/uploads/...` URLs. The repository includes a Free-plan `render.yaml`, migration startup script, and optional Resend HTTPS email delivery. Follow [the deployment checklist](docs/deployment.md) for project creation, required secrets, Google setup, and live verification.

A multi-stage [Dockerfile](Dockerfile) packages React and .NET together. [compose.yml](compose.yml) runs a **local development** app and Postgres:

```sh
docker compose up --build
```

Do not run Docker Compose and the native local PostgreSQL script on port 55432 simultaneously. Docker execution has not been verified in this session because Docker Desktop was not running.

## Verify

```sh
./scripts/test.sh
```

Tests create and delete only a uniquely named `gyg_tests_*` PostgreSQL database. To use another local/CI server, set `GYG_TEST_DATABASE` to an administrative connection permitted to create temporary test databases. They do not clear the development database. Three React regression tests additionally cover context switching, obsolete responses, and Saved card types. CI runs both test suites and builds React.

OpenAPI: **http://localhost:5080/openapi/v1.json** in Development. Example calls: [GetYourGigs.Api.http](src/GetYourGigs.Api/GetYourGigs.Api.http). Formatting tools are pinned in [dotnet-tools.json](dotnet-tools.json). Run `dotnet csharpier format src tests` at the repository root; run `npx prettier --write src` from `src/GetYourGigs.Web` for the frontend.

See [verification.md](docs/verification.md) for observed checks and their limits. This is a local MVP codebase, not an App Store/Play Store release or a production deployment. Google provider login and real recipient email delivery require your configuration and have not been claimed as verified.
